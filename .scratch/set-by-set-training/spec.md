# 逐组真实打卡与组间间歇倒计时

状态：**实现、自动集成验证与双轴复审完成；真机待验，整体部分完成**。确认日期：2026-10-14。

实施分支：`feat/set-by-set-training`。实际字段/API 见 implementation.md；下文保留锁定业务规则与原技术建议，自动验证结果见 acceptance.md，不能代替真机验收。

## 1. 问题与现状

训练者需要边训练边真实打卡，而不是仅填写一张目标表。

实施前代码现状（历史）：

- `utils/domain.js::snapshotSession()` 预填每组目标重量和次数，没有完成标记。
- `pages/training/training.js::renderExercises()` 把填全重量/次数当进度，目标预填可使新训练直接显示 100%。
- `onFinish()` 仅检查非跳过动作数，不检查实际打卡，无法区分“计划目标”与“真实完成”。
- `onPause()` 只离开页面；当前没有逐组状态、间歇或暂停冻结。
- `computeVolume()` 统计所有组；整项 `skipped` 会排除整个动作，无法表达“练了两组，只跳过剩余两组”。
- 草稿键为 `fitness:trainingDraft`。动作库加练通过 domain 追加草稿，返回训练页时重新读取。
- 原有离线草稿、快照解耦、提交队列、计划自身游标、动作媒体反查均可复用；不引入外部计时依赖。

## 2. 已确认业务规则

### 2.1 顺序与逐组确认

1. 按计划动作顺序推进：动作 A 全部组处理后，进入动作 B，不做循环组或超级组。
2. 每组必须先点“开始本组”，实际练完再点“完成本组”。同时只有一组处于训练中。
3. 目标重量、次数继续预填，可改为实际数据。填值、目标预填、时间流逝均不自动完成组。
4. 完成本组时校验：次数为正整数；重量为有限非负数字；自重动作空重量按 0 处理。普通动作空重量不能打卡。
5. 打卡计入实际成绩并立即本地保存。重复点击不得重复完成、创建多个间歇或重复统计。
6. 间歇结束只进入“待开始”，不得自动开始或完成下一组。

### 2.2 间歇与提醒

1. 默认间歇 90 秒；同动作组间和动作切换均休息；整场最后一个待练组后不再休息。
2. 提供增减秒数、暂停/继续间歇、跳过间歇。交互建议使用 `−15 秒 / +15 秒`，与澄清时示例一致。
3. 修改时长影响当前剩余间歇及本场后续间歇；下场恢复 90 秒。不得出现负数或非有限秒数；最小值到 0 时按间歇结束处理。
4. 前台到时播放短提示音、短振动，并展示“间歇结束，可以开始下一组”。页面提示始终保留；声音/振动失败不阻塞训练。
5. 跳过间歇是用户主动结束休息，不额外发“到时”声音；直接待开始。
6. 切后台、锁屏或去动作库时，未主动暂停的间歇按真实时间流逝。返回用时间戳校准；已过期则提示一次，不重开完整倒计时。
7. 主动暂停训练冻结间歇剩余秒数；恢复后从剩余秒数继续。训练中暂停则保留该组，恢复后继续当前组，不自动完成。
8. 不承诺锁屏/后台准时声音或系统通知；无需订阅消息、云端定时任务、通知授权。返回前台发现到时后可补一次前台提醒。
9. 页面销毁/进程重启后，从持久化草稿恢复业务状态；暂停态必须仍暂停。不得残留重复定时器或音频实例。

### 2.3 跳过、增删与纠错

1. 可显式跳过动作剩余组。已打卡组及其实际容量保留；完全没练的动作不计动作数与容量。
2. 跳过不算完成组，页面须单独标记。不能通过“全部跳过”得到一场有效训练。
3. 保留现有恢复动作入口：恢复未打卡的跳过组，不重置已完成组，恢复后重新纳入待练清单。
4. 允许加组、加练；新组未打卡，不继承完成状态。本场改动不回写计划。
5. 已打卡组可编辑实际重量/次数，仍须满足同一校验；不可删除。练过的动作不可整项移除，只能跳过剩余。
6. 未打卡的末组可删除，维持至少一组；当前训练中的组不得通过删除绕过打卡。完全未练动作可显式跳过或移除。
7. 下一组开始前，允许撤销最近一组完成：取消对应间歇，回到该组训练中，保留输入值。下一组开始后，只能改上一组数据，不能撤销完成。
8. 对跳过、删除、加练等列表变更，重新核对当前组和下一组，不因下标漂移跳过待练组或指错记录。恢复已跳过组也不得产生两个训练中组。

### 2.4 整场完成与历史兼容

1. 至少一组已打卡，且所有未跳过组均已打卡，才能显示可用的“完成训练”。空场次、全部跳过、仍有待练组时不得提交。
2. 所有待练组完成后，用户仍可先加组或加练；新增后再次禁用整场完成，直到完成新增组。
3. 最后点“完成训练”才保存整场、入提交队列、推进计划游标。仅完成某组、暂停、退出、间歇结束都不推进游标。
4. 完成在本地成立，云端失败排队重试。文案不得误称“只有云端提交成功才推进”。重复点完成、返回页面、网络重试不重复推进游标。
5. 已提交历史记录不改写。升级前进行中的旧草稿保留输入值，所有组视为未打卡，从第一组重新确认；原先整项跳过保留为跳过。
6. 草稿升级必须幂等：新草稿重进页面不清除已打卡状态、跳过状态或间歇状态。
7. 本轮不新增提前结束并计作完成、失败组、训练时长计秒型动作或弃训记录类型；未完成训练留草稿、不推进计划。
8. 本轮不改总时长既有口径：从整场开始至完成的真实经过时间，包含间歇和暂停；不新增净训练时长指标。

## 3. 状态流

```text
开始整场 / 恢复草稿
  → 当前组待开始
  → [开始本组] → 当前组训练中
  → [完成本组且数据合法] → 本组已打卡
      ├─ 还有待练组 → 间歇倒计时
      │    ├─ 暂停间歇 → 冻结 → 继续
      │    └─ 到时 / 跳过间歇 → 下一组待开始
      └─ 没有待练组 → 待整场确认
           ├─ 加组 / 加练 / 恢复跳过组 → 待开始
           └─ [完成训练] → 本地成立、队列、游标推进、小结

任一训练阶段 → [暂停训练] → 保存并冻结 → [继续训练] → 恢复原阶段
最近组已打卡且下一组未开始 → [撤销最近组] → 最近组训练中
```

训练阶段与每组结果分开：训练阶段表达“用户当前在做什么”；组结果表达“哪些实际做完、哪些显式跳过”。“所有组都有输入值”不是任何状态迁移条件。

## 4. 页面结构建议

复用 `pages/training/` 与现有设计变量、动作详情组件，不新增 tab。

```text
暂停训练                         本场经过 18m
计划名 / 训练日
已打卡 3 / 待练总量 12 组 · 已跳过 2 组

当前：杠铃卧推 · 第 2 / 4 组
[动作示意图与要领入口]
重量 kg [40]          次数 [10]
            [开始第 2 组]
开始后：    [完成第 2 组]

间歇态：    01:30
下一组：杠铃卧推 第 3 组
[−15 秒] [暂停 / 继续] [+15 秒]
[跳过间歇] [撤销最近组]

动作列表：完成组绿勾、当前组强调、待练组中性、跳过组单独标记
[加组] [动作操作：跳过剩余 / 恢复 / 移除未练动作]

底栏：[加练动作] [完成训练：有待练组时禁用]
```

- 当前组操作醒目且单一，避免列表中多个“开始”按钮同时可用。
- 进度以 `已打卡组 / (已打卡组 + 未跳过未打卡组)` 计算；跳过不冒充打卡，单独展示数量。分母为 0 时进度为 0，完成仍禁用。
- “训练中”与“间歇中”明确区分；倒计时使用 `mm:ss`，不能只靠颜色表达状态。
- 未练组可预填编辑，但不可越过当前组直接打卡；已完成组修改成绩不产生第二次间歇。
- 到时提示不弹强制确认框，不自动启动下一组。
- 小结复用现有容量、动作数、时长与比较；详情区分实际组与跳过组，不能将跳过组预填目标渲染成真实成绩。

## 5. 技术建议（原方案，实施契约见 implementation.md）

### 5.1 数据与纯逻辑

- 新草稿/新场次追加流程版本和逐组状态；保留重量/次数成绩模型。组状态建议区分 `pending / completed / skipped`，已开始但未完成的当前组由训练阶段记录。
- 训练草稿另存当前组引用、阶段、本场默认间歇、截止时间/冻结剩余秒数、最近可撤销组与该间歇是否已提醒。恢复必须依赖持久化状态，不能只靠页面变量。
- 组/动作引用需在增删后保持有效；可以稳定标识或受控重算实现，不先固化字段名或增添通用状态机库。
- 快照创建、新增动作、新增组、旧草稿升级都使用同一个组初始化规则；不得产生无标记的新组被误判为历史已完成。
- 草稿升级只操作本地草稿，不能遍历并“补完成状态”到历史 `sessions`。
- 状态迁移、当前组选择、校验、撤销窗口、跳过剩余、进度和整场门禁放入 `utils/domain.js` 纯函数；页面只收事件和渲染。
- 旧已提交记录按旧逻辑读取；新记录容量只计 `completed` 组，动作数只计含完成组的动作，跳过组预填值不计成绩。容量公式仍是常规 `Σ(weight × reps)`、自重 `Σreps`，判据仍只认原值 `body weight`。
- `computeVolume()`、整场统计、趋势及记录详情共用筛选规则。必须明确区分“旧已提交记录没有标记”和“新草稿未完成”，不能全局把“缺标记”当新组完成。
- 新提交快照保留组结果；计时器句柄、音频实例等运行时对象不得进入快照。草稿临时控制状态在提交时移除或转为只读最终状态。

### 5.2 时间、资源与生命周期

- 倒计时使用绝对截止时间：`剩余秒数 = max(0, ceil((截止时间 - 当前时间) / 1000))`。定时器只驱动显示，不以每次回调减 1 作为事实来源。
- 暂停保存剩余时间并清除有效截止时间；继续时用“当前时间 + 剩余时间”重建截止时间。
- `onShow` 校准时间；`onHide/onUnload` 停止页面定时器并清理音频资源，但非主动暂停不改变业务上的截止时间。
- 同一间歇提醒最多一次，状态先落本地再发提醒。计时结束、回前台、重复回调同时发生不得重响。
- 声音使用有使用权的小体积随包音频，离线可用，不依赖云存储音频。微信音频/振动 API、静音行为及清理方式在实施前查官方文档、实施后真机验证。
- 存储失败不能假装打卡成功；提交锁覆盖本地结束到小结全过程，云端重试不再次推进游标。

## 7. 非目标与风险

- 不做后台通知保证、订阅消息、社交、超级组/循环组、单组计时训练、云端间歇计时或每组联网。
- 不修改计划目标、动作主键、目录迁移版本、媒体快照规则、历史成绩；不新增训练净时长口径。
- 核心风险：预填与完成混淆、部分跳过抹掉真实成绩、下标变化指错当前组、草稿升级重置状态、后台回调重复提醒、队列重试重复推进计划。
- 新 session 增加状态会影响统计与详情，不能只改训练页面。后续实现完成一个逻辑单元后做聚焦代码审查。
- 暂无本地视觉设计图和可访问测试 URL，不预先宣称视觉验收通过；实施后按项目条件决定视觉代理验收，微信端真机验收不可被 Jest mock 代替。
