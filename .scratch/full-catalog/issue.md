# 动作库改为非 cardio 可用全量与官方原值筛选

**Spec 来源**：本文件（本轮 grilling 锁定）；合并进 `docs/spec.md` 动作库章节。架构取舍见 ADR-0008，词汇表见 `CONTEXT.md`。

## Problem Statement

训练者在动作库里只能看到 125 条精选动作，筛选按产品部位标签和器械归并桶，对不上数据集官方 `body_part` / `equipment` 原值。加练和改计划时找不到上游已有的力量动作；名称、GIF、要领也没有按字段完整性做发布闸门。

## Solution

把发布目录改为上游非 cardio 可用全量：排除 `body_part === cardio`，再减去锁定媒体排除清单里缺 JPEG、GIF 或中文要领的 ID。动作库筛选改为官方部位原值 + 器械原值动态枚举，胶囊多选，组内 OR、组间与搜索 AND。中文名以社区映射打底、手译覆盖，自动化只保证 id 唯一且 nameZh 非空。文本目录继续本地分片离线可读；媒体脚本可规划全量目标，真实 CloudBase 上传仍人工门控。

## User Stories

1. 作为训练者，我想在动作库里浏览上游全部非有氧动作，以便加练时不必受 125 条精选限制。
2. 作为训练者，我不想在动作库里看到跑步机、椭圆机等有氧条目，以便列表仍服务力量打卡。
3. 作为训练者，我想按官方身体部位筛选动作（背、胸、前臂、小腿、颈、肩、上臂、大腿、腰腹），以便分类与数据集一致。
4. 作为训练者，我想按数据集里实际出现的器械原值筛选（如 barbell、ez barbell、assisted），以便不会被归并桶藏掉。
5. 作为训练者，我想同时选多个部位或多个器械，以便一次找出「胸或肩」且「杠铃或哑铃」的动作。
6. 作为训练者，我想点「全部」清空该行筛选，以便迅速回到无约束列表。
7. 作为训练者，我想搜索词与部位、器械同时生效，以便缩小结果。
8. 作为训练者，我想用中文名、英文名或已有俗称别名搜到动作，以便在健身房快速找到目标。
9. 作为训练者，我想每条动作都有中文展示名，以便列表可读。
10. 作为训练者，我想打开详情时看到中文要领，以便离线也能对照步骤。
11. 作为训练者，我想列表继续只加载 JPEG 缩略图，以便滚动时不拉 GIF。
12. 作为训练者，我想详情继续按 GIF → JPEG → glyph 降级，以便媒体失败时仍能加练。
13. 作为训练者，我想结果仍分页显示并看到完整匹配数，以便判断筛得严不严。
14. 作为训练者，我想已有计划里的动作不会因为目录扩容被删掉，以便升级后训练日保持原样。
15. 作为训练者，我想新出现的动作由我自己加进计划，以便不被自动改计划。
16. 作为训练者，我想自重容量仍按器械原值 `body weight` 计算，以便筛选改原值后打卡数字不变。
17. 作为目录维护者，我想生成时锁定数据集与中文映射版本，以便校验可复现。
18. 作为目录维护者，我想缺源 JPEG/GIF 或中文要领的 ID 进入锁定排除清单，以便发布目录没有空详情。
19. 作为目录维护者，我想排除清单之外再出现媒体或要领缺口时生成失败，以便坏数据进不了主包。
20. 作为目录维护者，我想没有本地 images/videos 源目录时生成失败，以便不会把「JSON 有路径」当成「文件可访问」。
21. 作为目录维护者，我想上传脚本按最终目录规划每个动作的 JPEG 与 GIF，以便 dry-run 能报目标规模。
22. 作为目录维护者，我不想本轮自动对 CloudBase 执行全量上传，以便真实同步仍人工门控。
23. 作为产品维护者，我想退役精选白名单、热身/复合/模式标签对筛选的约束，以便全量目录不再依赖手写 tags。
24. 作为产品维护者，我想领域文档与测试契约改到新口径，以便不再把 125 条精选写成当前真相。

## Implementation Decisions

- 发布目录闸门改为：上游 `body_part !== cardio`，减去锁定媒体排除清单。不再使用精选白名单、目标肌群粗筛或 D 节策展排除。
- 精确条数以生成结果为准（非 cardio 候选约 1295）；文档与测试锁「非 cardio 且不在排除清单」，不把 1295 写成不可变常数。
- 每条动作仍是精简字段：`id` / `name` / `nameZh` / `equipment` / `bodyPart` / `target` / `imagePath` / `gifPath` / `instructionSteps` / `aliases`。主键仍是 4 位数字 id。
- `name` 必须等于上游英文原值。`nameZh` 来自中文映射，可被既有手译覆盖。生成闸门：id 唯一、每条 nameZh 非空。允许不同 id 共用同一中文名。
- `aliases` 继续只参与关键词搜索，不参与筛选、不改展示名。未覆盖的新动作别名为空数组。
- 「名称/GIF/要领正确」的自动验收：英文名与上游一致；nameZh 非空；`instruction_steps.zh` 去空后非空；`DATASET_DIR` 下 JPEG 与 GIF 文件 `lstat` 成功。不做动作语义或译名人工审校。
- 媒体排除清单是生成输入：源文件缺失的 id 写入清单并从发布目录剔除。清单外再缺则生成失败。无 images/videos 源目录则生成失败。
- 数据快照锁定：记录数据集版本、中文映射版本、排除清单与生成时间。更新上游必须重新生成并跑闸门。
- 文本目录继续本地 JS 分片、离线可读。超 2MB 主包再分包，本轮不改云端目录。
- 筛选只认上游原值。部位行 = 9 个非 cardio `body_part`。器械行 = 发布目录里实际出现的 `equipment` 原值，稳定排序；缺中文译名回退英文。不再提供杠铃/哑铃等归并桶，也不再提供二头/三头/臀/热身/复合。
- 检索语义：关键词 AND（部位组内 OR）AND（器械组内 OR）。空选或「全部」表示该维无约束。
- 动作库页胶囊点击切换多选；再点取消；点「全部」清空该行。筛选条件与 items/resultCount 必须一次提交，不得依赖 `setData` 回调再检索。
- 分页与预热保持 24 / 48 JPEG，列表不预取 GIF。
- 扩容不加计划迁移版本：现有计划动作仍可查，不因扩库删除。Session 零写入。volume 仍只认 `equipment === 'body weight'` 原值。
- 媒体同步脚本按最终目录规划 `imagePath` + `gifPath` 目标；真实上传/清理仍是人工验收，Jest 与 dry-run 不能代替。
- 测试缝：离线目录检索、生成器闸门、上传目标规划、动作库页一次提交检索。不把目录筛选塞进打卡 domain 模块。

## Testing Decisions

- 只测可观察行为：目录内容、检索结果、生成成功/失败、上传目标集合、页面一次提交后的筛选态与分页窗口。不断言临时变量。
- 目录：无 cardio；排除清单中的 id 不存在；其余非 cardio 均可 `findById`；每条 nameZh 与中文要领非空；id 唯一。
- 筛选：每个官方部位、每个实际器械原值各自非空；多选部位为并集；部位与器械、搜索为交集；别名仍能命中对应 id；归并桶与热身/复合筛选不再存在。
- 生成器：无源媒体目录失败；清单外缺文件失败；手译覆盖缺 nameZh 失败。可用夹具目录，不强制本机常驻 130MB 媒体。
- 上传脚本：目标数 = 最终目录 × 2；路径仍落在两个受管前缀。
- 动作库页：多选与「全部」清空；`applySearch` 一次提交条件与结果；首屏 24、滚动 +24。
- 计划读取：扩容后现有训练日动作仍在，不新增迁移版本。
- Jest 不代替真实微信开发者工具渲染，也不代替 CloudBase 最终集合。

## Out of Scope

- 有氧/计时训练与第二套 set 模型。
- 人工逐条核对动作语义、GIF 内容、译名对错。
- 本轮自动执行 CloudBase 全量上传或旧对象清理。
- 自定义上游不存在的动作或伪造 id。
- 自动把新动作写入用户计划。
- 改变 Session 快照、volume 口径、动作主键。
- 产品部位标签、热身/复合/模式筛选、器械归并桶。
- Gym visual 书面授权流程本身。
