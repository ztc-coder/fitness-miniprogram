# 思维指南

> **目的**:拓宽思考角度,提前发现容易被忽略的问题。

---

## 为什么需要思维指南

**大多数 bug 和技术债来自"没想到"**,而不是能力不足:

- 没想到分层边界处的数据格式差异 → 跨层 bug
- 没想到代码模式在重复 → 到处都是重复代码
- 没想到边界情况 → 运行时报错
- 没想到未来维护者怎么读这段代码 → 代码难以理解

这些指南帮你**在写代码之前问对问题**。

## 快速参考:思考触发点

### 何时该考虑跨层问题

- [ ] 功能涉及 3 个以上层级(如 页面 / db 层 / domain 层 / 云数据库)
- [ ] 数据格式在层与层之间发生转换
- [ ] 多个消费者需要同一份数据
- [ ] 不确定某段逻辑该放在哪一层
- [ ] 新增字段需要同时改变多处形状定义(如 Plan / Session 结构)
- [ ] 页面代码开始直接读取未经归一化的原始云端字段

→ 阅读[跨层思维指南](./cross-layer-thinking-guide.md)

### 何时该考虑代码复用

- [ ] 正在写的代码和已有代码很相似
- [ ] 同一模式已经重复出现 3 次以上
- [ ] 要在多处新增同一个字段
- [ ] **正在修改任何常量或配置**
- [ ] **正在新建一个工具/helper 函数** ← 先搜索!
- [ ] 多处代码各自手写同一种格式化/校验逻辑

→ 阅读[代码复用思维指南](./code-reuse-thinking-guide.md)

### 验证 AI 交叉审查结果时

- [ ] 审查者声称"用户输入可能是恶意的" → 检查真实数据来源(内部数据?还是外部输入?)
- [ ] 审查者提示"缺少校验" → 数据是否来自可信的内部来源?
- [ ] 审查者说"行为发生变化" → 看代码注释,是不是本来就是有意为之的设计?
- [ ] 审查者在测试里指出"bug" → 假设去掉被测的功能,测试是否仍然通过?如果是 → 这是一个空判断的测试(tautological test)

**AI 审查常见的误报模式**:
1. **信任边界混淆**:把项目内部数据(如打包进小程序的静态数据)当成不可信的外部输入
2. **忽略设计注释**:把代码注释里明确说明的有意行为标记为 bug
3. **变量误读**:没有追溯变量的真实定义就下结论

**验证规则**:每一条严重/警告级发现,在排优先级之前都必须对照真实代码验证。AI 审查的误报率大致按 35% 预估。

## 修改前置规则(重要)

> **改任何值之前,先搜索!**

```bash
grep -r "要改的值" .
```

这一个习惯能防住大多数"忘了同步改另一处"的 bug。

---

## 如何使用本目录

1. **写代码前**:快速浏览相关思维指南
2. **写代码中**:如果感觉逻辑重复或复杂,回来对照指南
3. **出 bug 后**:把新的教训补充进对应指南
