## Problem Statement

用户(个人自用)想要一个不依赖社交、不含多角色、不含支付/通知的力量训练打卡工具。现有健身 App 大多为多人社交场景设计,信息噪音大;用户需要的核心诉求是:按自定义的第 N 天循环(如推-拉-腿)推进训练,在健身房网络不稳定的环境下也能顺畅打卡,并且历史记录必须忠实于当时实际训练情况,不受后续计划调整影响。

## Solution

构建一个微信原生小程序 MVP:

- 训练计划以「第 N 天循环」建模,游标随打卡完成推进,漏练不打乱顺序。
- 打卡时把当天计划快照复制为独立 session,本地缓存整场训练,仅在结束提交时联网,无网自动排队重试。
- 动作库离线可读(文本精简打包进小程序,图片/GIF 走云存储按需加载),发布目录为上游非 cardio 可用全量（缺源媒体或中文要领的 id 进入锁定排除清单）；不是精选白名单。
- 记录 tab 提供按 session 时间线回看,以及后续单动作 volume/总次数趋势曲线。
- 静默 openid 登录,后端使用微信云开发 CloudBase(云数据库 + 云存储 + 云函数),前端为原生 WXML/WXSS/JS,无 TypeScript/跨端框架。

## 定位

- **个人自用**单用户闭环。
- 无社交、无多角色(不含私教/学员)、无支付、无订阅或系统通知；逐组训练允许前台提示音、振动与页面提示。

## 训练计划模型

- **第 N 天循环**(如 推-拉-腿),不绑定星期几。
- **完成驱动推进**:打卡完成才推进游标;漏练不打乱循环,游标 = 实际训练进度。
- **计划里只放训练日**,无"休息日"概念;休息靠不打卡自然体现。
- **可存多个计划,同一时刻只有一个 active**。
  - 游标是**每个计划自身的字段**,切回计划从上次离开处继续。
  - "active" 只决定首页显示哪个计划。
- 计划里动作用**动作级统一目标**:`{组数, 目标次数, 目标重量}`,四组共享同一目标。逐组差异靠打卡时自由填写兜住。

## 训练日 / 记录模型

- 训练日 = 有序动作列表,每个动作含 set 级数据。
- **set 成绩统一为 `{weight, reps}` —— 只做力量训练**,不做有氧/计时类。新流程已追加稳定组 id 与完成状态，输入值与完成确认分开；旧历史不补写状态。
- **自重动作**(判据:`equipment == "body weight"`)复用该模型,`weight` = 额外负重(徒手为 0 或空)。
- **开始训练 = 快照复制**:把当天计划复制成一条独立的 workout session，在副本上填实际数据；新方案中“逐组打卡”专指实际完成一组后的显式确认，快照生成和目标预填不算完成。
  - **记录不可变**:历史记录忠实于当时实际发生的训练,不受后续修改计划影响。
- 打卡时**可自由增删动作**(临时加练 / 跳过没练的),动作从动作库选。

## 打卡流程

- **单次训练本地缓存,结束时整体提交**一条 session。
  - 扛住健身房全程无网;仅"结束提交"那一刻需要网络,无网则排队重试。
- **原 MVP 历史**：曾无组间休息计时器，填写重量/次数后可整场提交；当前已由逐组训练替代，见 `.scratch/set-by-set-training/spec.md`。
- **当前逐组方案**：练完直接勾选任意组，可编辑、取消完成、增删未完成组。至少完成一组即可发起结束；存在待练组时确认跳过剩余，再保存实际成绩并推进计划。
- **手动间歇**：默认 90 秒，本场记忆；支持快捷时长、±15 秒、独立暂停、半屏面板与底部计时条。记录操作不打断计时；整场暂停禁用记录并冻结间歇，切后台按真实时间校准，不承诺后台准时提醒。
- 结束后给**整页完成小结**：完成组数 / 动作数 / 负重容量 / 自重次数 / 时长，复用 volume 计算并分单位与上次同类型训练对比。

## 动作库

结论来自动作库接入、非 cardio 可用全量与七类部位筛选需求。词汇表见 `CONTEXT.md`，主键与媒体托管见 ADR-0007，目录范围的历史决策见 ADR-0008。当前筛选与展示口径见 `.scratch/library-seven-parts/issue.md`。

- 数据源:[`hasaneyldrm/exercises-dataset`](https://github.com/hasaneyldrm/exercises-dataset)（MIT 文本 + 媒体单独条款）。中文名映射:[`wangmuerxiao/exercises-dataset-zh`](https://github.com/wangmuerxiao/exercises-dataset-zh) 的 `name_zh.json`。
- 取值范围:**发布目录 = 上游非 cardio 可用全量**。过滤仅 `body_part === cardio`（及 `category === cardio`）。耸肩、前臂专项、平衡设备、爆发变式、单侧与版本号重复一律放行。缺源 JPEG、源 GIF 或中文要领的 id 写入锁定排除清单，不进发布目录；清单外再缺则生成失败。精确条数以生成结果为准（非 cardio 候选约 1295）。
- **主键**:数据集 4 位数字字符串（如 `"0025"`）。现有 slug 计划读取时迁移到数字 id。目录迁移版本保持 **v5**：本轮扩容不升版本、不因新目录删除已有计划动作。历史 session 零写入。
- **中文名**:社区映射打底 + 手译覆盖；英文 `name` 必须等于上游原值，仅参与检索，不在界面作为副标题。自动闸门是 id 唯一且每条 `nameZh` 非空；允许不同 id 共用同一中文名。`aliases` 是目录一等字段，承载已有俗称 / 旧译名，参与关键词搜索，不参与部位筛选、不改展示名；未覆盖的新动作别名为空。
- **文本精简后打进主包**,本地分片、离线可读。字段:`id` / `name` / `nameZh` / `equipment` / `bodyPart` / `target` / `imagePath` / `gifPath` / `instructionSteps` / `aliases`（仅中文要领）。丢掉多语言原文与 `muscle_group`。超 2MB 再分包，本轮不把目录放到云数据库。
- **示意图 + 动作演示走 CloudBase**按需加载，不进主包、不热链 GitHub。动作库列表和打卡页只请求 JPEG 缩略图，详情弹层按 GIF → JPEG → glyph 降级。源文件可访问以 `DATASET_DIR` 下 JPEG/GIF `lstat` 为准，不以 JSON 路径非空为准；无源媒体目录则生成失败。
- **「标准动作」= 动作演示 GIF + 中文要领**。出现在动作库详情弹层与打卡页详情弹层；列表、今天/计划清单、记录页不自动加载 GIF。自动验收不判断动作语义或译名对错。
- **筛选**:部位一行按胸 / 背 / 肩 / 手臂 / 腿 / 腰腹 / 臀固定排序；`target === 'glutes'` 优先归臀，其余颈归肩、上下臂归手臂、上下腿归腿，所有非 cardio 动作各归一类。器械一行仍是目录实际出现的 `equipment` 原值，稳定排序，当前目录全部提供中文标签，不改变器械原值或归并语义。胶囊点击切换多选，点「全部」清空该行。匹配为搜索 AND（部位组内 OR）AND（器械组内 OR）。结果首屏 24 条，滚动每次追加 24 条，显示完整匹配数；当前页和下一页最多预热 48 张 JPEG。筛选条件与 items/resultCount 一次提交。详情显示同一部位归类；英文名及原值仍能搜索，但界面不显示英文动作副标题或英文标签，版权署名与网址保留。
- **媒体反查**:打卡页用 `exerciseId` 查动作库；不把路径写入 session。
- **数据版本**:生成锁定数据集 commit、中文映射 commit、排除清单与生成时间；更新上游须重跑生成与闸门。
- **验收边界**:仓库内 Jest/Page harness 覆盖非 cardio 可用全量目录、七类部位与器械原值多选筛选、分页窗口、生成闸门和同步脚本按最终目录规划的受管媒体目标；CloudBase 2,590 个对象已完成同步，仍需微信开发者工具确认真实 WXML 渲染/滚动与详情媒体加载。

## User Stories

1. 作为训练者,我想让计划按第 N 天循环推进,而不是绑定星期几,这样我可以按自己的节奏训练。
2. 作为训练者,我想让游标只在完成打卡后才前进,这样漏练一天不会打乱我的循环顺序。
3. 作为训练者,我想让游标是每个计划自己的字段,这样切换计划后再切回来能从上次离开的地方继续。
4. 作为训练者,我想同时保存多个计划,但只有一个是 active,这样首页始终清晰地告诉我该练哪个。
5. 作为训练者,我想计划里的动作用统一目标(组数/目标次数/目标重量),这样制定计划时不用逐组填写。
6. 作为训练者,我想在实际打卡时可以自由填写每组的实际数据,这样统一目标不会限制我的真实表现。
7. 作为训练者,我想计划里只放训练日、没有休息日概念,这样我的休息完全由自己安排,不用在计划里额外维护。
8. 作为训练者,我想训练日是一份有序动作列表,每个动作包含 set 级数据,这样结构清晰、一目了然。
9. 作为训练者,我想 set 模型统一为 `{weight, reps}`,这样力量训练的数据结构简单一致。
10. 作为练自重动作的训练者,我想自重动作复用同一个 set 模型(weight 表示额外负重),这样不需要维护第二套数据模型。
11. 作为训练者,我想开始训练时把当天计划复制成一条独立 session,这样临时调整不会影响原计划。
12. 作为训练者,我想历史记录忠实于当时实际发生的训练,不受后续修改计划影响,这样我可以信任自己的历史数据用于回顾和对比。
13. 作为训练者,我想打卡时可以自由增删动作(临时加练/跳过没练的),这样计划外的调整也能被记录下来。
14. 作为训练者,我想新增的动作能从动作库里选择,这样不用手动输入动作信息。
15. 作为训练者,我想单次训练全程本地缓存、结束时才整体提交,这样健身房没有网络也不影响我记录训练。
16. 作为训练者,我想仅在"结束提交"那一刻才需要联网,无网则自动排队重试,这样我不用操心提交时机。
17. 作为训练者，我想练完直接勾选任意组，自由修改重量次数、增减组，按需手动开始间歇；提前结束时确认跳过剩余，仅保存实际完成成绩。
18. 作为训练者,我想训练结束后看到整页完成小结(完成组数/动作数/负重容量/自重次数/时长),这样能立刻知道这次训练的强度。
19. 作为训练者,我想完成小结里能看到与上次同类型训练的对比,这样能感知自己的进步或退步。
20. 作为训练者,我想动作库从候选数据集中排除 cardio、冷门和重复变式,这样列表里只有和我训练相关的精选力量动作。

23. 作为训练者,我想记录 tab 提供按训练场次时间线倒序回看的视图,这样能快速找到最近的训练记录。

28. 作为训练者,我想底部有 4 个固定 tab(今天/计划/记录/我的),这样导航结构简单直观。
29. 作为训练者,我想首页"今天"卡片显示 active 计划当前游标指向的训练日和动作清单,这样一打开小程序就知道今天该练什么。
30. 作为训练者,我想首页有醒目的"开始训练"按钮,这样能立刻进入打卡流程。
31. 作为训练者,我想"计划"tab 能管理循环计划(增删动作、调整顺序),这样我可以按需调整训练安排。

## Implementation Decisions

- **Domain logic 模块(核心纯函数 seam)**:新建一个与 CloudBase SDK、WXML 渲染层解耦的纯逻辑模块(`utils/domain.js`),输入输出均为纯 JS 对象/数组,不依赖网络或小程序运行时 API。该模块至少包含以下子能力:
  - **游标推进(cursor advance)**:输入当前 plan(含 cycle 顺序、当前 cursor)与"是否完成打卡"事件,输出推进后的新 plan(游标 +1,循环到 cycle 末尾则回到开头)。漏练(未打卡)不改变游标。
  - **打卡快照(session snapshot)**:输入 plan 当前游标指向的训练日定义,输出一份独立的 session 草稿(深拷贝,不与 plan 共享引用),草稿允许增删动作、编辑每组 `{weight, reps}`。
  - **volume 计算**:输入一个动作的 set 列表,输出 `Σ(weight × reps)`;若动作 `equipment == "body weight"`,输出改为 `Σreps`。此函数同时用于打卡后的完成小结与记录 tab 的趋势曲线,保证口径一致。
  - **提交队列(pending submission queue)**:输入本地已完成但未提交成功的 session 列表与网络状态,输出下一步动作(立即提交 / 加入重试队列 / 重试),队列判定逻辑本身不发起真实网络请求,由上层(云函数调用封装)注入提交函数。
- **数据模型**:
  - Plan:`{id, name, cycleDays: [{dayId, name, exercises: [{exerciseId, sets, targetReps, targetWeight}]}], cursor, active}`。
  - Session(打卡快照):`{id, planId, dayId, startedAt, submittedAt, exercises: [{exerciseId, sets: [{weight, reps}]}]}`,一旦生成即与 plan 解耦,不因后续 plan 编辑而改变。
  - Exercise(动作库条目,只读离线数据):`{id, name, nameZh, equipment, bodyPart, target, imagePath, gifPath, instructionSteps, aliases}`。目录为非 cardio 可用全量（减去锁定排除清单）,`id` 为数据集 4 位数字字符串；`aliases` 承载已有俗称/旧译名并参与关键词搜索；`equipment == "body weight"` 是判断自重动作、切换 volume/总次数口径的唯一依据（筛选原值不改变该判据）。
- **架构分层**:UI 页面(WXML/WXSS/JS)与云函数入口都是 domain logic 模块之上的薄封装,不重复实现游标推进、快照复制、volume 计算、队列判定这几类核心规则,避免逻辑分散到多处。
- **动作库交付形式**:文本字段(`id/name/nameZh/equipment/bodyPart/target/imagePath/gifPath/instructionSteps/aliases`)精简后随小程序主包分片发布,本地离线可读;示意图与动作演示走 CloudBase 云存储按需加载,不进主包。筛选为七类部位 + 器械原值多选，列表显示 JPEG 缩略图并按 24 条递增分页,详情继续 GIF → JPEG → glyph；主键与媒体托管见 ADR-0007，历史范围决策见 ADR-0008，当前筛选见七类部位需求票。
- **动作库生成链**:
  - 发布目录闸门是非 cardio 减去锁定媒体排除清单,不再使用精选白名单或目标肌群粗筛。
  - 发布目录保留上游 `bodyPart` 与 `equipment` 原值；筛选用七类部位与器械原值，退役热身、复合、模式与器械归并桶。
  - `aliases` 仍是生成链的一等字段：既有手译与别名覆盖保留，搜索命中 `aliases`；别名不参与筛选、不改变展示名。
  - 生成锁定数据集与中文映射版本；源 JPEG/GIF 以本地文件存在为准。
  - 本轮扩容不升 v5、不按新目录裁剪已有计划动作。
- **打卡提交时机**:训练全程使用本地缓存(小程序本地存储),只有点击"完成训练并提交"时才触发一次网络请求写入 CloudBase;网络不可用时交由提交队列逻辑排队重试,不阻塞本地记录的生成。
- **身份**:使用微信静默 openid 登录,不做登录墙、不做账号体系之外的身份校验。

## Testing Decisions

- 测试 domain 公开纯函数、Page 用户事件/生命周期、记录与提交队列公开边界（仅 mock wx、云端、时间和存储）,不测试内部实现细节(例如不断言中间变量,只断言函数返回值和产生的副作用数据结构)。
- 覆盖模块:
  - 游标推进:验证完成打卡后游标前进、循环到末尾回到开头、未打卡时游标不变。
  - 打卡快照:验证快照与原 plan 无共享引用(修改快照不影响 plan,反之亦然)、快照允许增删动作。
  - volume 计算:验证常规动作 `Σ(weight×reps)`、自重动作 `Σreps`、空 set 列表返回 0。
  - 提交队列:验证有网络时立即提交、无网络时进入队列、重试后成功从队列移除。
- 目录测试断言可观察行为：无 cardio；排除清单中的 ID 不存在；其余非 cardio 可 `findById`；每条 `nameZh` 与中文要领非空；id 唯一；七类部位完整覆盖且互斥、实际器械原值各自非空；多选为组内 OR、组间与搜索 AND；俗称别名仍能搜到对应 ID。
- 迁移测试保持 v5 版本号；历史裁剪测试仅保留为 skipped 的迁移记录。扩容后新增契约是：已有训练日动作仍可查，不自动删除；Session 零写入。
- 媒体脚本测试覆盖最终目录规划的受管对象（每条 JPEG+GIF）、路径安全、受管前缀删除边界、最终集合校验与失败重试。
- 页面级分页测试覆盖全量匹配数、七类部位与器械原值多选后的渲染窗口、JPEG fileID，以及筛选条件与结果一次提交。
- Jest 是仓库内确定性验证工具：domain、目录、页面级 Page harness、数据库迁移和媒体同步纯函数均可在 Node 中运行；真实 WXML 渲染、微信开发者工具滚动和 CloudBase 远端集合不由 Jest mock 代替。

## Out of Scope

- 组间休息计时器已从原 MVP 范围外移入逐组训练增补方案，已实现；当前范围外仍包含锁屏/后台准时系统通知。
- 社交功能、多角色(私教/学员)、支付、通知系统。
- 有氧/计时类训练记录(set 模型只支持 `{weight, reps}`)。
- Gym visual 媒体正式授权流程本身(属于法务/商务事项,不是本 spec 的实现范围,但 UI 需为授权状态与署名留出位置)。
- 趋势曲线的 top weight / 估算 1RM 指标(仅预留切换入口,具体计算逻辑不在本次范围)。
- 精简 JSON 实际体积测量与分包方案(记录为待办,不在本 spec 的实现任务内)。
- 自定义上游不存在的动作或伪造四位 ID。
- 改变动作主键、重写已提交历史记录 schema。逐组训练允许对新草稿/新记录追加完成状态，容量公式不变，仅统计已打卡组；旧记录保持原读取口径，详见增补方案。
- 为三分化/四分化/五分化建立互相独立的目录。
- 自动改写用户计划以注入新增动作（新增动作由用户自行添加）。
- 公开再分发 Gym visual 媒体；ADR-0007 的个人自用与署名约束不变。
