# 健身训练小程序 MVP — 需求规格

> 本文档是一次 grilling 会话(逐项决策访谈)后达成的共享理解,作为后续设计与实现的依据。
> 状态:需求已锁定；精选目录已扩容到 136 条（含第 10 个产品标签「热身」）、计划迁移升到 v3、分页缩略图和媒体同步脚本均已实现，真实微信开发者工具与 CloudBase 媒体验收仍待人工完成。

## 定位

- **个人自用**单用户闭环。
- 无社交、无多角色(不含私教/学员)、无支付、无通知系统。

## 训练计划模型

- **第 N 天循环**(如 推-拉-腿),不绑定星期几。
- **完成驱动推进**:打卡完成才推进游标;漏练不打乱循环,游标 = 实际训练进度。
- **计划里只放训练日**,无"休息日"概念;休息靠不打卡自然体现。
- **可存多个计划,同一时刻只有一个 active**。
  - 游标是**每个计划自身的字段**,切回计划从上次离开处继续。
  - "active" 只决定首页显示哪个计划。
- 计划里动作用**动作级统一目标**:`{组数, 目标次数, 目标重量}`,四组共享同一目标。逐组差异靠打卡时自由填写兜住。

## 训练日 / 记录模型

- 训练日 = 有序动作列表,每个动作含 set 级数据。
- **set 模型统一为 `{weight, reps}` 单一类型 —— 只做力量训练**,不做有氧/计时类。
- **自重动作**(判据:`equipment == "body weight"`)复用该模型,`weight` = 额外负重(徒手为 0 或空)。
- **打卡 = 快照复制**:开始训练时,把当天计划复制成一条独立的 workout session,在副本上填实际数据。
  - **记录不可变**:历史记录忠实于当时实际发生的训练,不受后续修改计划影响。
- 打卡时**可自由增删动作**(临时加练 / 跳过没练的),动作从动作库选。

## 打卡流程

- **单次训练本地缓存,结束时整体提交**一条 session。
  - 扛住健身房全程无网;仅"结束提交"那一刻需要网络,无网则排队重试。
- **无组间休息计时器**(MVP 不做,后期评估)。
- 结束后给**轻量完成小结**:动作数 / 总容量 / 时长 + 与上次同类型训练的对比。复用 volume 计算。

## 动作库

结论来自后续 grilling（完善动作库 / 接入数据集）。词汇表见 `CONTEXT.md`，架构取舍见 ADR-0007。

- 数据源:[`hasaneyldrm/exercises-dataset`](https://github.com/hasaneyldrm/exercises-dataset)（MIT 文本 + 媒体单独条款）。
- 取值范围:从数据集候选池中按 `data/curated-catalog.js` 的精确 `exerciseId` 白名单保留 **136 条**常用动作（规格区间约 100–140 条）；排除 `cardio`、冷门/重复/平衡设备及无必要的单侧变式。名字含 stretch 的条目不因关键词自动保留。
- **主键**:数据集 4 位数字字符串（如 `"0025"`）。现有 slug 计划读取时迁移到数字 id，未知或已移出精选目录的计划动作由目录迁移清理。目录迁移版本为 **v3**：直接按最终目录可查性删除动作，**不建立旧 ID → 新 ID 的 replacement 映射**；随之出现的空训练日和空计划被删除，历史 session 零写入。
- **中文名**:社区映射打底 + 手译覆盖；英文 `name` 作副标题。`aliases` 是已实现的目录一等字段，承载中文俗称 / 旧译名（如「倒蹬」「龙门架」「下拉」），参与关键词搜索，不参与部位筛选、不改展示名。
- **文本精简后打进主包**,离线可读。字段:`id` / `name` / `nameZh` / `equipment` / `bodyPart` / `target` / `imagePath` / `gifPath` / `instructionSteps` / `aliases`（仅中文要领）。丢掉多语言原文与 `muscle_group`。
- **示意图 + 动作演示走 CloudBase**按需加载，不进主包、不热链 GitHub。动作库列表和打卡页只请求 JPEG 缩略图，详情弹层按 GIF → JPEG → glyph 降级。
- **「标准动作」= 动作演示 GIF + 中文要领**。出现在动作库详情弹层与打卡页详情弹层；列表、今天/计划清单、记录页不自动加载 GIF。
- **筛选**:器械一行 6 桶（杠铃/哑铃/绳索/器械/自重/其他，语义归并）+ 精选元数据的部位一行 **10 个标签**，筛选行固定顺序 11 项（全部 / 胸 / 背 / 肩 / 二头肌 / 三头肌 / 腿 / 腰腹 / 臀 / 热身 / 复合动作），搜索、器械、部位为 AND。复合动作与热身都是与具体部位重叠的标签，选中它们不隐藏具体部位标签下的可发现性。结果首屏 24 条，滚动每次追加 24 条，显示完整匹配数；当前页和下一页最多预热 48 张 JPEG。
- **媒体反查**:打卡页用 `exerciseId` 查动作库；不把路径写入 session。
- **验收边界**:仓库内 Jest/Page harness 覆盖 136 条目录筛选（含 11 项筛选顺序与热身重叠）、分页窗口、v3 迁移和同步脚本的 272 个受管媒体目标；真实 WXML 渲染/滚动、CloudBase 最终媒体集合和旧媒体清理不能由 Node mock 或 dry-run 代替。

### ⚠️ 发布前置阻塞项

- **媒体版权归 Gym visual,克隆仓库 ≠ 获得授权**（与 ExerciseDB 权利主张冲突）。
- 个人自用本轮可加载真实媒体并署名；**正式上线前必须**:取得 Gym visual 书面授权 + 保留 `© Gym visual — https://gymvisual.com/` 署名 + 遵守 180×180 分辨率限制 + 不得把仓库媒体镜像再分发。

## 信息架构

- **底部 4 个 tab:今天 / 计划 / 记录 / 我的**。
- **首页(今天)** = "今天该练什么"卡片(显示 active 计划当前游标指向的训练日 + 动作清单)+ **开始训练**按钮。
- **计划 tab**:管理循环计划(增删动作、调顺序)、动作库入口。
- **记录 tab**:上述两个回看视图。
- **我的 tab**:设置、个人信息。

## 身份 / 存储 / 技术栈

- **静默 openid 登录**,无登录墙,打开即用。
- 后端:**微信云开发 CloudBase**(云数据库 + 云存储 + 云函数),免运维。
- 前端:**微信原生小程序**(WXML/WXSS/JS),不引入 TypeScript / 跨端框架。

## 待办(非阻塞,发布前处理)

1. **Gym visual 媒体授权** —— 上线前必须落实；本仓库不能代替法务或真实 CloudBase 验收。
2. **精简 JSON 体积实测** —— 裁剪后确认能否落进 2MB 主包,装不下则走分包。
3. **社区中文名抽检** —— 映射质量一般,明显错译后续手修。
4. **微信开发者工具端到端验收** —— 需人工/外部环境确认真实 WXML 绑定、滚动、图片失败降级与详情媒体加载。
5. **CloudBase 媒体集合验收** —— 需真实云凭据确认 136 条目录的 272 个受管对象已上传、最终集合一致，并清理 `exercises/images`、`exercises/videos` 下的陈旧对象；dry-run 不能代替。

## 当前实现与验收边界

仓库内已实现并由 Jest 覆盖 136 条精选目录、10 个部位标签（含热身）与复合标签筛选、24 条分页/48 条有界预热、v3 计划目录迁移（含离线恢复）以及媒体同步脚本的纯函数和失败重试。真实微信开发者工具行为、真实 CloudBase 最终媒体集合和旧媒体清理仍是 `ready-for-human` 验收项；不得以 Node mock 或 dry-run 代替这些确认。
