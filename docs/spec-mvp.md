# 健身训练小程序 MVP — Spec

> 当前实现状态：精选动作库（136 条，10 个部位标签含「热身」）、v3 计划迁移、分页 JPEG 缩略图及媒体同步脚本已落库；真实微信开发者工具与 CloudBase 媒体集合验收仍由 `.scratch/catalog-expansion/issues/05-integration-acceptance-and-docs.md` 追踪。

## Problem Statement

用户(个人自用)想要一个不依赖社交、不含多角色、不含支付/通知的力量训练打卡工具。现有健身 App 大多为多人社交场景设计,信息噪音大;用户需要的核心诉求是:按自定义的第 N 天循环(如推-拉-腿)推进训练,在健身房网络不稳定的环境下也能顺畑打卡,并且历史记录必须忠实于当时实际训练情况,不受后续计划调整影响。

## Solution

构建一个微信原生小程序 MVP:

- 训练计划以「第 N 天循环」建模,游标随打卡完成推进,漏练不打乱顺序。
- 打卡时把当天计划快照复制为独立 session,本地缓存整场训练,仅在结束提交时联网,无网自动排队重试。
- 动作库离线可读(文本精简打包进小程序,图片/GIF 走云存储按需加载),为三/四/五分化提供 136 条精选常用动作（规格区间约 100–140 条）；不是上游全量目录。
- 记录 tab 提供按 session 时间线回看,以及后续单动作 volume/总次数趋势曲线。
- 静默 openid 登录,后端使用微信云开发 CloudBase(云数据库 + 云存储 + 云函数),前端为原生 WXML/WXSS/JS,无 TypeScript/跨端框架。

## User Stories

1. 作为训练者,我想让计划按第 N 天循环推进,而不是绑定星期几,这样我可以按自己的节奏训练。
2. 作为训练者,我想让游标只在完成打卡后才前进,这样漏练一天不会打乱我的循环顺序。
3. 作为训练者,我想让游标是每个计划自己的字段,这样切换计划后再切回来能从上次离开的地方继续。
4. 作为训练者,我想同时保存多个计划,但只有一个是 active,这样首页始终清晰地告诉我该练哪个。
5. 作为训练者,我想计划里的动作用统一目标(组数/目标次数/目标重量),这样制定计划时不用逐组填写。
6. 作为训练者,我想在实际打卡时可以自由填写每组的实际数据,这样统一目标不会限制我的真实表现。
7. 作为训练者,我想计划里只放训练日、没有休息日概念,这样我的休息完全由自己安排,不用在计划里额外维护。
8. 作为训练者,我想训练日是一份有序动作列表,每个动作包含 set 级数据,这样结构清晰、一目了然。
9. 作为训练者,我想 set 模型统一为 `{weight, reps}`,这样力量训练的数据结构简单一致。
10. 作为练自重动作的训练者,我想自重动作复用同一个 set 模型(weight 表示额外负重),这样不需要维护第二套数据模型。
11. 作为训练者,我想开始训练时把当天计划复制成一条独立 session,这样临时调整不会影响原计划。
12. 作为训练者,我想历史记录忠实于当时实际发生的训练,不受后续修改计划影响,这样我可以信任自己的历史数据用于回顾和对比。
13. 作为训练者,我想打卡时可以自由增删动作(临时加练/跳过没练的),这样计划外的调整也能被记录下来。
14. 作为训练者,我想新增的动作能从动作库里选择,这样不用手动输入动作信息。
15. 作为训练者,我想单次训练全程本地缓存、结束时才整体提交,这样健身房没有网络也不影响我记录训练。
16. 作为训练者,我想仅在"结束提交"那一刻才需要联网,无网则自动排队重试,这样我不用操心提交时机。
17. 作为训练者,我想 MVP 阶段不做组间休息计时器,这样功能范围保持精简(后期再评估)。
18. 作为训练者,我想训练结束后看到轻量完成小结(动作数/总容量/时长),这样能立刻知道这次训练的强度。
19. 作为训练者,我想完成小结里能看到与上次同类型训练的对比,这样能感知自己的进步或退步。
20. 作为训练者,我想动作库从候选数据集中排除 cardio、冷门和重复变式,这样列表里只有和我训练相关的精选力量动作。
21. 作为训练者,我想精选动作库的文本字段(中英文名/器材/部位/目标肌群/媒体路径/中文要领)精简后打进小程序包体,这样离线也能浏览动作库。
22. 作为训练者,我想动作的 JPEG 缩略图和 GIF 按需从云存储加载,这样不会让小程序包体过大。
23. 作为训练者,我想记录 tab 提供按训练场次时间线倒序回看的视图,这样能快速找到最近的训练记录。
24. 作为训练者,我想记录 tab 后续提供单动作的进步曲线视图,这样能追踪某个具体动作的长期变化。
25. 作为训练者,我想进步曲线默认按 volume(Σ重量×次数)展示,这样能综合衡量训练强度的变化。
26. 作为练自重动作的训练者,我想自重动作的进步曲线用总次数(Σreps)展示,这样即便没有负重数据也能看到进步。
27. 作为训练者,我想进步曲线预留多指标切换能力(top weight/volume/估算 1RM),这样未来能按不同维度分析。
28. 作为训练者,我想底部有 4 个固定 tab(今天/计划/记录/我的),这样导航结构简单直观。
29. 作为训练者,我想首页"今天"卡片显示 active 计划当前游标指向的训练日和动作清单,这样一打开小程序就知道今天该练什么。
30. 作为训练者,我想首页有醒目的"开始训练"按钮,这样能立刻进入打卡流程。
31. 作为训练者,我想"计划"tab 能管理循环计划(增删动作、调整顺序),这样我可以按需调整训练安排。
32. 作为训练者,我想"计划"tab 提供动作库入口,这样调整计划时能方便地挑选动作。
33. 作为训练者,我想"我的"tab 提供设置和个人信息管理,这样账号相关的操作有统一入口。
34. 作为训练者,我想使用静默 openid 登录、无登录墙,这样打开小程序即可直接使用,没有额外的登录步骤。
35. 作为产品维护者,我想后端使用微信云开发 CloudBase(云数据库+云存储+云函数),这样免运维、降低单人维护成本。
36. 作为产品维护者,我想前端使用原生 WXML/WXSS/JS,不引入 TypeScript 或跨端框架,这样保持技术栈精简、减少构建链路复杂度。
37. 作为产品负责人,我想在正式上线前取得 Gym visual 的书面媒体授权、保留署名并遵守分辨率限制,这样避免版权风险。
38. 作为产品负责人,我想在上线前验证精简后的动作库 JSON 能否落进 2MB 主包,这样能提前规划是否需要分包。

## Implementation Decisions

- **Domain logic 模块(唯一测试 seam)**:新建一个与 CloudBase SDK、WXML 渲染层解耦的纯逻辑模块,输入输出均为纯 JS 对象/数组,不依赖网络或小程序运行时 API。该模块至少包含以下子能力:
  - **游标推进(cursor advance)**:输入当前 plan(含 cycle 顺序、当前 cursor)与"是否完成打卡"事件,输出推进后的新 plan(游标 +1,循环到 cycle 末尾则回到开头)。漏练(未打卡)不改变游标。
  - **打卡快照(session snapshot)**:输入 plan 当前游标指向的训练日定义,输出一份独立的 session 草稿(深拷贝,不与 plan 共享引用),草稿允许增删动作、编辑每组 `{weight, reps}`。
  - **volume 计算**:输入一个动作的 set 列表,输出 `Σ(weight × reps)`;若动作 `equipment == "body weight"`,输出改为 `Σreps`。此函数同时用于打卡后的完成小结与记录 tab 的趋势曲线,保证口径一致。
  - **提交队列(pending submission queue)**:输入本地已完成但未提交成功的 session 列表与网络状态,输出下一步动作(立即提交 / 加入重试队列 / 重试),队列判定逻辑本身不发起真实网络请求,由上层(云函数调用封装)注入提交函数。
- **数据模型**:
  - Plan:`{id, name, cycleDays: [{dayId, name, exercises: [{exerciseId, sets, targetReps, targetWeight}]}], cursor, active}`。
  - Session(打卡快照):`{id, planId, dayId, startedAt, submittedAt, exercises: [{exerciseId, sets: [{weight, reps}]}]}`,一旦生成即与 plan 解耦,不因后续 plan 编辑而改变。
  - Exercise(动作库条目,只读离线数据):`{id, name, nameZh, equipment, bodyPart, target, imagePath, gifPath, instructionSteps, aliases}`。目录由精确精选白名单维护（当前 136 条）,`id` 为数据集 4 位数字字符串；`aliases` 承载中文俗称/旧译名并参与关键词搜索；`equipment == "body weight"` 是判断自重动作、切换 volume/总次数口径的唯一依据（筛选桶归并不改变该判据）。
- **架构分层**:UI 页面(WXML/WXSS/JS)与云函数入口都是 domain logic 模块之上的薄封装,不重复实现游标推进、快照复制、volume 计算、队列判定这几类核心规则,避免逻辑分散到多处。
- **动作库交付形式**:文本字段(`id/name/nameZh/equipment/bodyPart/target/imagePath/gifPath/instructionSteps/aliases`)精简后随小程序主包发布,本地离线可读;示意图与动作演示走 CloudBase 云存储按需加载,不进主包。筛选行 11 项（全部/胸/背/肩/二头肌/三头肌/腿/腰腹/臀/热身/复合动作），列表显示 JPEG 缩略图并按 24 条递增分页,详情继续 GIF → JPEG → glyph；详见 ADR-0007。
- **打卡提交时机**:训练全程使用本地缓存(小程序本地存储),只有点击"完成训练并提交"时才触发一次网络请求写入 CloudBase;网络不可用时交由提交队列逻辑排队重试,不阻塞本地记录的生成。
- **身份**:使用微信静默 openid 登录,不做登录墙、不做账号体系之外的身份校验。

## Testing Decisions

- 只测试 domain logic 模块的外部行为(输入/输出),不测试内部实现细节(例如不断言中间变量,只断言函数返回值和产生的副作用数据结构)。
- 覆盖模块:
  - 游标推进:验证完成打卡后游标前进、循环到末尾回到开头、未打卡时游标不变。
  - 打卡快照:验证快照与原 plan 无共享引用(修改快照不影响 plan,反之亦然)、快照允许增删动作。
  - volume 计算:验证常规动作 `Σ(weight×reps)`、自重动作 `Σreps`、空 set 列表返回 0。
  - 提交队列:验证有网络时立即提交、无网络时进入队列、重试后成功从队列移除。
- Jest 是仓库内确定性验证工具：domain、目录、页面级 Page harness、数据库迁移和媒体同步纯函数均可在 Node 中运行；真实 WXML 渲染、微信开发者工具滚动和 CloudBase 远端集合不由 Jest mock 代替。

## Out of Scope

- 组间休息计时器(MVP 明确不做,后期评估)。
- 社交功能、多角色(私教/学员)、支付、通知系统。
- 有氧/计时类训练记录(set 模型只支持 `{weight, reps}`)。
- Gym visual 媒体正式授权流程本身(属于法务/商务事项,不是本 spec 的实现范围,但 UI 需为授权状态与署名留出位置)。
- 动作库趋势曲线的 top weight / 估算 1RM 指标(仅预留切换入口,具体计算逻辑不在本次范围)。
- 精简 JSON 实际体积测量与分包方案(记录为待办,不在本 spec 的实现任务内)。
