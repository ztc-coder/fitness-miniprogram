# ADR-0004：打卡采用快照复制，历史记录不可变

- 状态：已采纳
- 日期：2026-09-17
- 相关文档：`docs/spec.md`（训练日 / 记录模型、打卡流程）

## Context（背景）

计划是**长期演进**的：动作会增删、顺序会调整、目标重量会变。
而训练记录的价值在于**忠实还原当时实际发生了什么**，用于回顾与对比进步。

如果把 session 存成"对 plan 当前状态的引用 + 实际数据覆盖"，
那么事后改一次计划，所有历史记录的含义都会跟着变——
历史数据失去可信度，趋势曲线也不再可比。

另一个约束是打卡现场：健身房里经常要临时加练、跳过没练的动作。

## Decision（决策）

**开始训练 = 把当天计划快照复制成一条独立 session**，在副本上填实际数据。

- `snapshotSession(plan)` 对当前游标指向的训练日做**深拷贝**（`JSON.parse(JSON.stringify(...))`），
  与 plan **不共享任何引用**。
- 快照生成时用 `buildSessionSets()` 预填目标数据（`{weight: targetWeight, reps: targetReps}`）作为默认值，
  打卡时可自由改写。
- 快照内允许**自由增删动作**（`addSessionExercise` / `removeSessionExercise`）与增删组，
  临时加练从动作库（`pages/library`）选。
- 标记跳过用 `skipped: true`，跳过动作不计入动作数与总容量。
- 计划侧的 `cursor` 只在**提交完成**后通过 `advancePlanCursor()` 推进。

## Consequences（后果）

**正向**

- 历史记录不可变：改计划不影响任何既有 session。
- 完成小结的"与上次同类型训练对比"（同 `planId` + `dayId`）口径稳定可比。
- 打卡现场的临时调整天然被记录，不需要"先改计划再练"。

**代价 / 需要接受**

- 数据冗余：每条 session 都存一份动作名与器械快照，云数据库存储略增（本项目量级可忽略）。
- `planId` 与 `dayId` 只作为**对比分组键**，不保证在 plan 中仍存在；读取历史时不能反查 plan 取名字。
- 深拷贝意味着 session 上的修改不会回写 plan——这是设计意图，但需要开发者明确知道"改计划要去计划页"。

**相关规则**

- 快照与游标推进是两件事：**快照不推进游标**，只有提交完成才推进（完成驱动，漏练不打乱循环）。
- 提交失败时 session 进入 pending queue 重试，但**本地记录已经成立**，不因网络失败而丢失。
